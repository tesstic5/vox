## 2 · A8 — classes and group appointments: what shipped

The design of record is `PLAN-A8-CLASSES.md`; the whole thing rests on two rules that
the code follows everywhere:

> **A seat is an ordinary booking** that carries a `sessionId`, and **the session — not
> the seat — is what occupies the diary.**

Everything good follows from that. Reminders, confirmations, invoices, notes, consent
and the client's own manage link keep working on a seat *because it is a booking*, and
eight people share one room without eight clashes because the room is held once.

**Records.** A class is a **service** with `capacity >= 2` (unset or 1 = one-to-one, so
every existing service is untouched). `classSessions[]` holds one occurrence: service,
instructor, site, room, start, length, capacity, status. A seat is a `bookings[]` row
with `sessionId`.

**Surfaces.**

- **Desk** — `/dashboard/classes`: the upcoming sessions with `taken/capacity`, a
  creation form (service · instructor · site · date · time · places), and a roster
  opened per session (`?session=…`) where a person can be added by name and taken off.
  A session is called off from the roster.
- **Diary** — `/dashboard/calendar` draws a session as **one dashed block with its
  count** (`class 3/8`) on the practitioner's and the room's row, not eight overlapping
  appointments. Moving or resizing it is refused with a sentence, not silently ignored.
- **Desk board** — "Classes today", above "Needs a decision", with the count and how
  many are already here.
- **Public page** — `/book/<slug>` gains a **"Classes you can join"** section below the
  services: one card per session with what is left, the day and time, the instructor and
  the room; taking a place asks for name, number and consent and returns a receipt with
  the reference and the calendar link. A stranger cannot see the roster, and cannot buy
  a place in another practice's class.
- **Client's own link** — a seat's manage page says it is a place in a class and shows
  the time; `canChange` is false and the API refuses a move (`409`), because moving one
  seat out of a session is not a thing — cancelling returns the place to the class and
  texts nobody.

**Contracts** (all of them exercised by the gate):

```
GET  /api/v1/classes                  → sessions, classes, sites, instructors, rooms, range, totals
POST /api/v1/classes   {action:create} 201 · {action:cancel}   (date+time site-local, capacity >= 2)
GET  /api/v1/classes/{id}             → session + roster + seatsLeft
POST /api/v1/classes/{id} {action:add-seat|remove-seat}
GET  /api/public/workspaces/{slug}/booking → += classes[] {sessionId, serviceName, instructor,
                                              site, room, startsAt, durationMinutes, capacity,
                                              seatsLeft, local}
POST …/booking {sessionId, name, number, consentSms} → 201 new · 200 {already: true}
```

**Product rules the build added, beyond the audit's one line:**

- The **class hour is occupied** — the availability engine refuses a private booking in
  it (`409` "…is on at that time.") and never offers that hour in a slot search. Room
  pickers see sessions too (`lib/server/rooms.ts`).
- **Never one too many** — the capacity wall is enforced on the last seat under a real
  concurrency window; the fourth person into a three-place class gets `409` naming the
  count, and a repeat joiner gets `200 {already: true}`.
- **A cancelled session is not a delete** — every seat is released, each holder is
  texted that it is off (with the reason, if given), the session leaves the public page
  and the board, and the hour returns to the diary.
- **A class service cannot be deleted out from under a session** — `deleteService`
  answers `{because: "classes", upcoming: N}` while a non-cancelled session is still to
  come, and the route says "class session(s)" in its refusal. Found while sweeping: a
  service *had* vanished from under a cancelled session, which is the hole this closes.

## 3 · The gate, and the walk

**`scripts/class_check.py` — 40 checks, part of the suite.** It proves the refusals as
much as the features: creating with 1 place (`400 "…at least 2 seats"`), with an
instructor who does not run the service (`400`, named), on an hour already taken

card — and fails on any console error or any claim the API does not back. It now
**stages its own class when the diary has none** (a service, an instructor linked to it,

## 4 · The tidy: the orphan rule and the provider-pointer fix

Both were carried from the tidy bundle and are now built, run and *proved*.

- **The orphan-session rule.** A class session whose service no longer exists cannot be
  named, joined or cancelled by title — the same debris as an invoice pointing at a
  client who is gone. `scripts/tidy-probe-orgs.ts` now sweeps those sessions and their
  seats along with the probe ones, and says so: `3 class session(s) (3 orphaned)`.
  The proof-of-hole row (`ses_518f9d630e5200ff`, cancelled, service long gone) is gone.
- **The provider-pointer fix.** Removing a service left its id dangling on the
  practitioner who ran it — `svc_73be868996fb7369` was still on Priya Raman's
  `serviceIds` after the service was deleted, which the roster screen shows as a service
  that does not exist. The rule is now general: **a service id that is not in the file is
  stripped from every practitioner's list**, whether this run removed the service or an
  earlier one did. Reported per person:
  `stripped 1 service reference(s) naming a service that is not in the file, from 1 practitioner(s) — Priya Raman → svc_73be868996fb7369`.

Three applies ran this turn (19:56, 20:21, 20:45 UTC — the last after the suite's own workspaces), each preceded by a dry run and each
followed by a second dry run that reports **"nothing to do"** — idempotent, and now
including `dangling service references` in that sentence. The last apply removed 57

## 5 · What I did not do, and why

- **No separate public classes endpoints.** The audit's need is met inside the existing
  booking route (`GET` gains `classes[]`, `POST` accepts `sessionId`); a second public
  surface would be a second thing to keep in step.
- **No rebuild of A4.** It shipped under D4/D5; only the proof was missing.
- **Three `Caller` client rows are left in the demo database.** They are real product
  behaviour — an unknown inbound number gets a record — created by the call checks, and
  they carry no appointments, invoices or notes. Out of scope here; a rule for them would
  have to tell a genuine unknown caller from a probe one, which the tidy cannot yet do.
